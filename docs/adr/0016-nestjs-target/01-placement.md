### Placement

The developer writes the controller and implements the generated interface of each resource (ADR 0007 `handlers`), as ADR 0012 "Your controller, the generated utilities around it" shows: `@TasksNest.updateTask() update(@TasksNest.updateTask.input() input: Tasks.UpdateTaskInput)`, with `import * as TasksNest from '.../tasks/nestjs'` and `import type * as Tasks from '.../tasks/types'`. Codegen emits, per api, under the target entry's `out`:

- A module middleware, bound to the routes of the generated route table, that opens the request context (`AsyncLocalStorage`, ADR 0012 "Open tenancy") and runs the step 1 checks that belong to the contract (the per-route body limit and the media type, below) and installs the outgoing response check (below). It writes its refusals itself in the api's error format, since an exception thrown by a middleware reaches only global filters.
- Per operation, a composite method decorator built with `applyDecorators`: the verb and the full contract path with `Version(VERSION_NEUTRAL)`, `SetMetadata` with the operation id and its access kind (the route metadata a native guard reads through `Reflector`, ADR 0012 "Native security layers"), `UseGuards` with the seampact guard, `UseFilters` with the seampact filter, the response mark of the reply path (below), and, applied first, the handler wrapper (below). It registers no interceptor. It carries no `HttpCode`: the reply path writes every status.
- The guard runs steps 2 to 5: authenticate (over the raw body for a signed identity), principal requirements, scopes outermost first, requirements in declared order. It records the checked request and the grant on the request context. Guards run after middleware and before interceptors and pipes, and the module moves the seampact guard after every guard the app sets on the route ("The NestJS stages").
- The guard and the handler wrapper wrap every hook call (ADR 0012 "Failures inside hooks"): a NestJS denial (`ForbiddenException`, `UnauthorizedException`) thrown inside a decide hook answers the requirement's first declared denial code, and any other exception thrown or rejected by a hook is a 500 with `onUnexpectedError` called; both leave as generated contract exceptions, so the seampact filter answers them and no app filter sees a hook's error.
- The handler wrapper replaces the controller method in place, keeping its name, its arity and the metadata decorators written below the composite set on it. On a request routed to its operation it answers 500 unless the input pipe checked the input, then runs the idempotency claim or replay and calls the method. In the default reply mode it then runs step 10: undeclared status, projection of restricted output fields, stripping of undeclared fields from the IR shape, derived headers, the derived ETag and 304, and the write of the reply; it returns no value, so NestJS calls the method directly and adds no interceptor path. In the interceptor mode it returns the method's result, and the reply interceptor runs step 10 and the write. Called anywhere else (a unit test, another handler calling it), it is the method itself.
- Per operation, a param decorator made with `createParamDecorator` whose value is the output of the seampact input pipe it carries: steps 6 to 8, input validation in one pass with the `validators` link's `input` validator over path, query, headers and body as recorded by the guard, restricted input fields and sort keys, and principal bindings. The pipe ignores the value NestJS extracts and any app pipe returned before it; it never uses the app's global `ValidationPipe` (ADR 0012 "The check order"). Besides `input()`, the `path()`, `query()`, `headers()` and `body()` param decorators exist for the parts its input declares: each reads its part of the input the `input()` pipe checks, steps 6 to 8 run once per request, shared by every input param of the method, and a method with only part params passes the boot check's input-param rule.
- In the interceptor mode only, the reply interceptor, registered by the api's module as an `APP_INTERCEPTOR`: on the api's contract routes it runs step 10 on the value NestJS's interceptors inside it pass on, and writes the reply; elsewhere it passes the call through. The module moves it to the front of the app's global interceptors in its `configure`, as it moves its guard last.
- The filter of the api's error format, the dynamic module registering the hooks, and the boot check (below).

The two per-operation decorators are named by the operation (ADR 0007 `operation` role): the composite is the operation's name, `createTask()`, and the param decorator is its `input` property, `createTask.input()`. They live in this target's module of the api, apart from the types link's module, so a declared schema of the same words (`CreateTask` in the reference contract) or the `CreateTaskInput` type never shares their scope (ADR 0007 section 7). Inside this target's output, its fixed exports (below) are shadowed names of ADR 0007 section 5 for the operation decorators, so an operation named `responses` gets `responses_()`.

Route order is the app's: NestJS on Express registers a controller's routes in the order its methods are declared and matches the first, so a parameter route declared before a static sibling of the same method (`GET /tasks/:taskId` before `GET /tasks/search`) shadows it, and the member operation runs its checks on the action's requests. The composite cannot reorder them; the developer declares the static route's method first.

Steps 1 to 8 and 10 run the request checks of `@seampact/server-runtime`, imported, not copied into the generated tree (ADR 0025); the placement file is the package's `/nestjs` export, and this target writes only the per-api module over it. Each api's generated tree holds `nestjs.ts`, `routes.ts`, `handlers.ts`, `hooks.ts`, `index.ts` and, with `nativeDocs`, its docs module. A NestJS app on CommonJS loads the package's CommonJS build.

Two apis of one app share the runtime, so what tells them apart is generated per api. `nestjs.ts` declares the api's `ContractException` subclass and hands it to the boundary: each api's filter answers the runtime's own errors and its own api's `ContractException`, never another api's, which matches neither api's filter and answers NestJS's default 500. The exported name stays `SeampactModule`, while the class carries the api's type name (`TasksSeampactModule`, `TasksServiceSeampactModule`), as NestJS logs it.
