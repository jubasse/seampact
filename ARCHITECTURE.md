# Architecture

This guide is the map for a new contributor: how the compiler runs, where each folder lives, and the files to touch for the four common changes. It states no decision of its own. Each section names the document that does, so read that document before you change anything.

- Product decisions: `docs/decisions.md` (cited as `A<n>`).
- Design: `docs/adr/` (cited as ADR `<n>`).
- Current packages and one line per source directory: `docs/agents/cartography.md`, generated by `node scripts/cartography/cli.ts --write`.
- Setup, the gate and git flow: `CONTRIBUTING.md`.

## 1. The compiler flow

The source of truth is the YAML contract. The compiler turns it into the IR (the intermediate representation), one JSON document per api, and every output reads the IR, never the YAML. The steps run in a fixed order (ADR 0006, section "1. Stages and passes"):

```text
source YAML -> load -> validate -> tree -> access -> derive -> link -> finalize -> IR -> targets
```

All compiler directories below are under `packages/core/compiler/src`.

- load (`load`): reads the workspace files and builds, per api, one merged raw tree from the api file, base, shared file, packs, includes and `$file` content. It resolves each name in the layers allowed to see it, records the source map, and refuses the YAML pitfalls. It also enforces root containment, refuses prototype keys and applies size and depth limits.
- validate (`validate`): checks the raw tree against the authoring JSON Schemas and reports refused schema keywords with their reasons.
- tree (`passes/tree/nodes`, `passes/tree/schemas`): the first pass. It writes the draft IR fields: the api tree, conventions, packs, schemas, scalars, enums and extension keys.
- access (`passes/access/identity`, `passes/access/rights`): the second pass. It writes identities, schemes, headers, rights, rules, scopes and per-operation requirements.
- derive (`passes/derive/wire`, `passes/derive/errors`): the third pass. It writes the derived wire members, errors and natures. The derivation table and the derivation roles are held as data in `derivations`.
- link (`passes/link`): a workspace pass that sees the IRs of every api. It produces diagnostics only, such as the relays superset check. Apis run through derive on their own, in relay order (`workspace`).
- finalize (`finalize`): takes a complete draft IR and assigns canonical ids and ordering, checks id collisions, validates against the IR JSON Schema, and writes the serialised IR and its side table (ADR 0004).

A step that reports an error stops the pipeline after it completes, so later passes always get consistent input, while every error of the failing step is still reported. Diagnostics (`diagnostics`) carry a rule id of the form `seampact/<step>/<rule>`, a message, a fix sentence and an origin that the side table turns into file, line and column (ADR 0006, section "4. Diagnostics"). The pass interface and the field ownership of each pass are in ADR 0006 sections 2 and 3; the orchestrator and its default parts are in `pipeline`.

Around the compiler, the other core packages read the IR: `openapi` writes the OpenAPI 3.1 documents, `lint` runs rules over the IR, `diff` classifies changes between two contract versions, `codegen-core` is the API generators are written against, and `cli` is the `seampact` command. `spec` holds the JSON Schemas of the YAML files and of the IR with their types, and the naming vectors.

## 2. Folders and groups

Rule (ADR 0009, section "Repository layout"): npm packages live at `packages/<group>/<name>`, the directory named after the package name suffix, in one pnpm workspace. The groups are `core`, `targets`, `packs` and `runtime`.

| Path | What it holds |
|---|---|
| `packages/core/*` | Exists today: `cli`, `codegen-core`, `compiler`, `diff`, `lint`, `openapi`, `spec`. Role `core` in the package manifest. |
| `packages/targets/` | Later group: one generator per framework or language, for example `targets/codegen-zod` for `@seampact/codegen-zod`. Not created yet. |
| `packages/packs/` | Later group: data-only convention packs (ADR 0008), for example `packs/pack-hal`. Not created yet. |
| `packages/runtime/` | Later group: the hooks, helper and adapter packages that generated code depends on at run time (ADR 0009, section "Package roles"). Not created yet. |
| `jvm/` | One Gradle build, one subproject per artifact. |
| `php/` | One directory per Composer package, `php/<name>`, each with its own `composer.json`. |
| `fixtures/` | Test inputs and expected outputs, shared by the tests (`loader`, `validate`, `passes`, `reference`, `draft`). |
| `scripts/` | Repository tooling: `cartography`, `checklist`, `hooks`, `ir-models` (Kotlin and PHP models), `package-rules`, `workspace`. |
| `docs/` | `decisions.md`, `adr/`, `agents/`, `conformance/` (checklist and proofs), `grammar/` (the authoring grammar, one file per section) and `ir/` (the IR, one file per section). |

Every package has exactly one role (`core`, `target`, `hooks`, `helper`, `adapter`, `pack`, `tool`), recorded in its manifest so CI can check the dependency rules in ADR 0009, section "Dependency rules". The package list planned for 1.0 is in ADR 0009, section "Package list for 1.0".

Every new source directory gets a header the cartography reads: a leading `//` comment in its `index.ts` whose first sentence says what the directory holds, or a one-line `README.md` when it has no `index.ts`. After adding one, run `node scripts/cartography/cli.ts --write` and commit `docs/agents/cartography.md`.

## 3. Recipes

Each recipe lists the files in order and the test to write first. Where the source documents do not say, the recipe says so. Nothing here is a new rule.

### 3.1 Add a compile rule

A compile rule is a check inside one pass that reports a diagnostic. There is no single document that lists the steps of this recipe; the order below follows ADR 0006 and the repository layout, and the points marked "not decided yet" are open.

1. Pick the step that owns the rule. The pass that writes a field is the pass that checks it (ADR 0006, section "3. Field ownership"). A rule whose subject is the authoring YAML shape belongs to validate, and the JSON Schema comes from the grammar modules under `packages/core/spec/src/authoring/grammar`.
2. Write the test first, next to the check, for example `packages/core/compiler/src/passes/access/identity/schemes.test.ts`. It must fail before the check exists. Test the behaviour: the source that breaks the rule yields one diagnostic with the expected rule id, and the valid source yields none.
3. Add a fixture directory under `fixtures/passes/<half>/<name>/` holding an `api.yaml` and the expected output, the way `fixtures/passes/access-identity/catalogues` does.
4. Write the check in the pass directory. Its diagnostic has the rule id `seampact/<step>/<rule>` in kebab case, a one-sentence message and a one-sentence fix (ADR 0006, section "4. Diagnostics"). Rule ids are stable and documented.
5. Document the rule in the grammar section under `docs/grammar/` that states the behaviour, when the rule enforces a grammar statement.
6. Record the fixture and tests in `docs/conformance/proofs/<lane-id>.yaml` when the rule proves a checklist item (see `docs/conformance/proofs/p1-loader.yaml` for the format). Never edit `docs/conformance/checklist.yaml`.

Not decided yet: where the list of rule ids is documented, and whether a new rule needs an entry in a registry. No document states either.

### 3.2 Add an IR member

The IR is change-controlled (ADR 0005, section "1. Two steps"; AGENTS.md says an IR change is asked of the lead, never worked around). Each IR change is its own small PR, merged before any work that needs it. The PR does the following, in this order:

1. Write the test first. The IR type and invariant tests fail until the schema changes: `packages/core/spec/src/ir/types.test.ts` checks the generated types, and a new value of a deciding member updates the struct's invariant and its partition in `packages/core/spec/src/ir/invariants.ts`, which fails the partition test until it does (`packages/core/spec/schemas/ir/CHANGE-TEMPLATE.md`, rules the reviewer checks).
2. Edit the IR JSON Schema under `packages/core/spec/schemas/ir/`. Classify the change as additive, tightening or breaking (ADR 0005, section "4. What is additive and what is breaking"). A new member that an older reader would silently ignore, and so generate a weaker check, is guarded by the exact `irRevision` match before 1.0, and by a feature or kind name from 1.0.
3. Raise `IR_REVISION` by one in `packages/core/spec/src/ir/version.ts`.
4. Regenerate the TypeScript types: `UPDATE_IR_TYPES=1 pnpm vitest run packages/core/spec/src/ir/types.test.ts`.
5. Regenerate the Kotlin models: `node --import ./scripts/ir-models/register.ts scripts/ir-models/cli.ts --write`. CI regenerates the native models and fails on any difference (ADR 0005, section "5. Readers and the seam"). The PHP models are regenerated in the same PR (ADR 0005, section "1. Two steps"); the command is not written in the template, so it is not decided yet in these documents.
6. Regenerate the golden IR files. The golden IR of the reference contract changes only in an IR change PR (ADR 0005, section "5. Readers and the seam").
7. Add the changeset: copy `packages/core/spec/schemas/ir/CHANGE-TEMPLATE.md` to `.changeset/<branch>.md` and fill the "IR change" section (irRevision old to new, classification, one row per field or kind, and what a target must do).
8. Update the IR section under `docs/ir/` that describes the member.

Work that needs the member (a pass that writes it, a target that reads it) starts only after this PR merges.

### 3.3 Add a target

A target is a separate package the consumer installs explicitly; the CLI never depends on or bundles one (ADR 0009, Context). Steps:

1. Do not start target work before the IR freeze gate of ADR 0005, section "1. Two steps" is met. Whether that gate is met today is tracked in `docs/decisions.md` and the handoff, not in these documents.
2. Create the package at `packages/targets/<name>`, for example `packages/targets/codegen-zod` for `@seampact/codegen-zod`, with role `target` in its manifest (ADR 0009, sections "Repository layout" and "Package roles"). Give its `index.ts` the directory header. JVM and PHP targets use `jvm/` and `php/<name>` instead.
3. Write the first test before the generator: the target's output for the reference contract fixture under `fixtures/reference`. The conformance and determinism rules are in ADR 0015.
4. Write the generator against `@seampact/codegen-core` (`defineTarget`, file writer, formatting hook, provider seam, version checks; ADR 0009, section "Package list for 1.0"). Compose with other targets through the provider seam, never through package dependencies (ADR 0009, section "The provider seam"). The dependency rules are in ADR 0009, section "Dependency rules".
5. Meet the obligations of ADR 0012, section "Target obligations": the per-framework items it lists, and for every target the per-route body limit as a generated check and query decoding from the raw query string.
6. Declare the target in the compatibility matrix and make it resolvable from the app config (ADR 0009, sections "Target resolution from the app config" and "Artefacts and the compatibility matrix").
7. Add the target's own ADR, which states its obligations besides its placement (ADR 0012, section "Target obligations" says each target's own ADR does).

Not decided yet: the exact file layout inside a target package, and the file names of its fixtures. The ADRs describe obligations, not a scaffold.

### 3.4 Add a pack

A pack is data only: YAML files with the same structure as the convention and declaration sections an api may write, plus the `pack` manifest (`name`, `version`, `extends`) and its `derive` entries. It contains no code (ADR 0008, section "A pack is data only").

1. Write the conformance fixtures first. Each first-party pack ships with its own conformance fixtures (ADR 0008, section "First-party packs in 1.0"). The test applies the pack to a small contract and checks the IR.
2. Create `packages/packs/<name>`, for example `packs/pack-hal` for `@seampact/pack-hal`, with role `pack` in its manifest. Its `package.json` names the YAML entry file, and its version is written once, in the manifest; the compiler refuses a `package.json` whose version differs (ADR 0008, section "A pack is data only").
3. Fill only the slots ADR 0008 allows (section "What a pack may set") and respect what stays core (section "What stays core"). The compiler validates every value with located diagnostics.
4. Check the layering: packs apply in the order of ADR 0002 section 2, `extends` first; settings are overridden leaf by leaf; declarations are never overridden (ADR 0008, section "Applying packs: order and overrides").
5. For a format pack, add its presets to `docs/grammar/15-first-party-pack-presets.md` (ADR 0008 points to ADR 0002 section 15 for the presets).
6. A pack that needs a code-level rule ships a separate lint plugin package; the pack never depends on it (ADR 0008, section "A pack is data only").

Not decided yet: the pack scaffold (file names inside the package) and how first-party packs are embedded in the standalone binary beyond the statement in ADR 0008 that they are.

## 4. Before you open a PR

Run `pnpm install --frozen-lockfile && pnpm gate && node scripts/checklist/cli.ts check && node scripts/cartography/cli.ts --check` and keep the tree clean. A stale cartography map is fixed with `node scripts/cartography/cli.ts --write`.
