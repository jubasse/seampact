### Exceptions on contract routes

A generated exception answers through its own `render()`, which Laravel's handler calls before any render callback of the app, a catch-all included (spike). It implements `ShouldntReport`, so the app's reporting stays quiet. An app `$exceptions->map()` that replaces it is the app's choice; the outgoing check judges the result.

Every other exception is rendered by the app's own handler, untouched. The boundary middleware then reads `$response->exception` on the reply and answers, in the api's format, with the role of:

- `AuthenticationException`: `unauthenticated` (401) whatever the `Accept` header: on a contract route the provider's render callback answers it before Laravel builds a redirect to `login`, so it never redirects and never becomes a 500 when no `login` route exists. Laravel's `auth` middleware builds its guest redirect while it builds the exception, with `route('login')` by default, which throws without that route; the boundary wraps the app's guest redirect (`Authenticate::redirectUsing`) so it answers none on a contract request and the app's own elsewhere. The boot check refuses an exception handler without `renderable`, where the 401 callback cannot be registered;
- `AuthorizationException` (the `can` middleware, a Policy): `forbidden` (403), or the role of its status when the denial sets one and the operation declares a code for it (`denyAsNotFound()`: `notFound`), else `forbidden`;
- `TokenMismatchException` and `OriginMismatchException` from `PreventRequestForgery`: `csrfInvalid` (403, where Laravel answers 419);
- `ThrottleRequestsException`: `rateLimited` (429), keeping `Retry-After` and the `X-RateLimit-*` headers;
- `PostTooLargeException` from `ValidatePostSize`: `payloadTooLarge` (413);
- `ModelNotFoundException` and every `RecordsNotFoundException` (`findOrFail()`, `firstOrFail()`): `notFound` (404);
- the `HttpException` 503 of `PreventRequestsDuringMaintenance`: `serviceUnavailable` (503, grammar 05 roles), keeping `Retry-After`;
- any other `HttpException`, as `abort()` throws from a handler or an app middleware: the role of its status, `unauthenticated` (401), `forbidden` (403), `notFound` (404), `rateLimited` (429) or `serviceUnavailable` (503).

Each of them answers by one rule, shared with every server target (ADR 0016): the code of its role when the operation declares one; else the operation's single code of the exception's status, or of its role's status when it carries none (`ModelNotFoundException` takes 404, as `abort(404)`); either one with the params its role binding renders from the role's data (IR section 7) when they hold every required param, or without params when that code declares no required one (a param with a default is not required); else the api's 500, logged. The `rateLimited` role's data is `retryAfterMs`, the delay of the first usable `Retry-After` of the framework's reply, then of the exception's own headers, in delta-seconds (capped at 9007199254740991 ms) or any of RFC 9110's three HTTP-date forms read as UTC (a past date is 0). It fills `retryAfterMs` of `api.rate_limited`, required or optional, whether or not a bucket rule declares a retry header; without a usable value, a code that requires it is the 500 too. So `abort(418)` on an operation with one 418 code answers that code, and a status with two codes, or one whose params are required, is a 500. An access hook (authenticate, resolve-scope) that throws an exception of this map keeps its role. Any other exception that no contract reply rendered is the api's 500 too, in every `responses` mode, so Laravel's error page and its debug trace never reach the client outside debug. Under `app.debug` only, such an exception, a bypassed boundary or a failed boundary step goes to Laravel's own handler and its error page, after the boundary's log line (which then names the message and file:line) and `onUnexpectedError`. This differs from Spring on purpose: Spring's resolver leaves an unknown exception to the app's `@ExceptionHandler` and judges that reply, whereas here an app exception's own `render()` is the api's 500 even when it writes a declared code; the mapping goes by exception class, then by the status of an `HttpException`, and this status mapping is on by default, as Laravel's own `abort()` rendering is. A generated exception renders only on a contract request; an exported `renderContractError($request, $exception)` for an app's own handler waits for a consumer that needs it.
