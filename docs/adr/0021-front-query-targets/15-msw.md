### MSW

`@seampact/codegen-msw` writes Mock Service Worker 2 handlers per api, typed through the `types` link as the fetch client is: `mocks.ts` holds `createMocks({ baseUrl })`, which returns per operation `handler`, `reply(status, body, init?)`, `error(code, params?, init?)` and `resolve(resolver)`, and `handlers`, every default handler with the most specific path first, for `setupServer` and `setupWorker` alike; `runtime.ts` is copied beside it. A handler path is the contract path with its literal text escaped for MSW, so `tasks:batch` matches only itself; a static segment MSW cannot escape (one holding `*`, or ending in `:` and digits) is refused by name (`path.segment.literal`). A handler lets through a request that a more specific route of the same method matches, so an override that `use` puts first never answers for a literal sibling such as `/tasks/search`. The handlers answer what the fetch client reads and nothing it refuses: they reuse the client's operation plan, so a form the client refuses is refused here, and a success envelope member, page fact or error member the mock cannot fill is refused by name (`mock.envelope.member`, `mock.page.fact`, `mock.error.member`). The paging styles rendered are those whose facts the handler result gives, the cursor styles and their `next` link; a style whose facts the server computes, such as the Laravel and Spring packs' numbered pages, stays refused by name. A reply is written as the server writes it: the payload in the format's envelope, a page's facts where the client reads them (a cursor in the `next` link, the request's own query with the cursor replaced), and an error in the api's error format, its code's own members filled at generation, its params merged, with the retry header and `no-store` the operation derives. A default handler answers the operation's first success example, as the handler returns it (a page example, the item array, as the page's items); an operation with none throws `MissingMockReply`, which MSW answers as a 500 naming the operation and how to give it a reply, so nothing is invented. Checking the request is refused by name (`options.validateRequests.unsupported`). The `front-msw` consumer, on `front` alone, runs the fetch client against the handlers in a node project and in the browser project, with no server: an example answers, a missing one fails until the test replies, a page reply carries its cursor and an error override reaches the client typed.
