### Exceptions on contract routes

NestJS hands each exception to exactly one filter, the first whose `@Catch()` types match, looking at the route's filters, then the controller's, then the global ones (the last registered first). A route-scoped filter that caught everything would therefore hide the app's own filters on every contract route. The seampact filter on the composite catches only the generated contract exceptions and the framework refusals it maps; every other exception follows NestJS's own path through the app's method, controller and global filters, untouched. Non-contract routes are never touched.

The framework refusals mapped at step 1: `UnauthorizedException`, `ForbiddenException`, and a 429 `HttpException` such as `@nestjs/throttler`'s `ThrottlerException`, each to the role of its status. NestJS picks a filter by its `@Catch()` types and a picked filter cannot decline, so the seampact filter never lists `HttpException` itself, which would take an exception of a status the operation does not declare from the app's filters: it lists the generated contract exceptions, the two classes above, a generated class whose `static [Symbol.hasInstance]` matches an `HttpException` of status 429, so the generated code does not import the throttler, and one matching an `HttpException` whose status the request's operation declares (below). Since the filter is bound on the method, NestJS picks it before the app's controller and global filters for every status the operation declares: an app's global `@Catch(NotFoundException)` or `HttpException` filter no longer sees those exceptions on contract routes, while an app `@UseFilters` written above the composite still comes first. These mappings apply only to refusals raised outside seampact's hooks (an app guard, the throttler); a refusal whose status the operation does not declare is a 500, as for a hook (ADR 0012 "Failures inside hooks"). An app filter renders a contract error with the exported `renderContractError(host, error)`, which writes it in the api's format through the boundary's reply path.

On a contract route, an `HttpException` thrown by a handler, a service, a pipe or an app guard takes the code of its status's role first, as the PHP targets map `abort()` and `HttpException`: 401 `unauthenticated`, 403 `forbidden`, 429 `rateLimited`, 503 `serviceUnavailable`; else the operation's one code of that status (`NotFoundException` the `notFound` code, a `ThrottlerException` the one 429 code of an operation with no `rateLimited` code); else a 500. Two codes of one status answer 500 reported to `onUnexpectedError`, since the exception cannot say which code it means. A code whose params have a required member, the role's code included, answers only when the boundary can fill them: on a 429, a `rateLimited` code whose required params are only `retryAfterMs` takes it from the `Retry-After` (delta-seconds or an HTTP-date) that the throttler set on the reply (`Retry-After-<name>` for a named `@nestjs/throttler` throttler) or that the exception carries; any other such code answers 500 reported to `onUnexpectedError`, whose message names `ContractException(code, params)`; the app's filters never write on a contract route. The Express, Fastify and Hono boundaries map a framework 401, 403 or 429 by the same rule. A status the operation does not declare stays with the app's filters. `ContractException(code, params)` is the typed way to answer any declared code; a code the operation does not declare answers its 500, reported to `onUnexpectedError`.
