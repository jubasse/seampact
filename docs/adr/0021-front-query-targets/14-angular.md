### Angular

`@seampact/codegen-angular` renders the same plan for Angular 22 with `query: fetch` only; another `query` value is refused as `options.query.invalid`, and `state` (`ngrx` or `ngrx-signals`) without the `service` artefact as `artefact.service.needed`. `queries.ts` is the shared plain fetch module. Its artefact `service` (default on, needing `queries`) adds `http-client-fetch.ts`, a `fetch` that sends through the app's `HttpClient` (so its interceptors, XSRF settings and `withFetch()` apply) and answers with a `Response` the client reads as the platform fetch's (it decodes text by the reply's charset where `fetch().text()` always reads UTF-8): an HTTP error status is an answer, a request that reached no server a `TypeError`, an abort an unsubscribe. `service.ts` holds `provide<Api>Api(config)`, the client config without `fetch`, and the `<Api>Api` class it provides, with no decorator so it needs no Angular compiler step: its `client`, its `queries`, and per operation a member. A query member takes its request as a function, read in a `computed` compared by the key request, and returns `{ data, error, isLoading, refetch }` over Angular's `resource()`, which aborts the read when its injector is destroyed and on a request change, and after that `refetch` does nothing; it needs an injection context or an `injector` option. On the server platform its request stays absent, so no read leaves the server, unless the caller passes a `transferId`, which reads there and hands the data to the browser through `resource()`'s transfer id. A mutation member, the retry rule and the refusals are those of Vue's plain fetch composables, over signals. An operation whose member would be `client` or `queries` is refused by name (`names.collision`). With `state: ngrx` (NgRx 22, `@ngrx/store` and `@ngrx/effects` peers), `ngrx.ts` adds per resource of the plan one `createActionGroup` (`<Resource>Actions`, source `<Api>/<resource>`, so two apis in one store never share an action type; the operations with no resource in `<Api>ApiActions`, source `<Api>`), with per operation the events `<op>` (`request`, and `call`, required when the client method requires a timeout), `<op>Success` (`request`, `data`) and `<op>Failure` (`request`, `error`, the operation's typed error), named in camel case so the action creators keep the operation's name; `<Api>Effects`, a functional effect per operation that sends the call through the `<Api>Api` service's fetchers and dispatches its success or failure, an unexpected rejection included, so no error ends the effect; and `provide<Api>Effects()`. Reads are grouped by their key request (`groupBy`, each group closed once none of its reads waits, so no group outlives its reads): the next read of the same request aborts the one still waiting, which ends in its failure with the abort error, so every action gets an outcome and a reducer's loading flag always clears; reads of different requests of one operation run side by side, since an effect serves the whole store, not one reader. A write flattens with `mergeMap`, so writes run side by side and each resolves on its own, as `mutate` does, with the action as its attempt, which gives each action one idempotency key; a write action whose operation takes one also accepts `call.idempotencyKey`, sent instead, so the app retries by dispatching again with the same key and the server runs the write once. There is no platform check: an effect sends wherever the app dispatches, the server included, as the app's own act (the reader's server rule does not apply); an app keeps reads off the server by dispatching in the browser. No reducer, selector or state type is generated (A36). Two groups with one name, and two events with one name in a group (an operation named after another's success or failure), are refused (`names.collision`). With `state: ngrx-signals` (NgRx Signals 22, `@ngrx/signals` peer), `ngrx-signals.ts` adds per operation a `signalStoreFeature`, `with<Op>()`, that the app composes into its own `signalStore`: its `withState` adds the slice `<op>`, the operation's latest call as `OperationSlice` (`status` `idle`, `pending`, `success` or `error`, its `request`, and its `data` or typed `error`), and its `withMethods` adds `send<Op>(request, call?)`, which sends through the `<Api>Api` service's fetchers and resolves to the slice its call settled, never rejecting. Reads go through the same `latestReadPerRequest` and `outcomeOf` flows as the effects: the next read of the same request aborts the one still waiting, which resolves to its failure with the abort error, and reads of different requests run side by side, each resolving on its own while the slice follows the latest call sent. On the server platform a read sends nothing and resolves to the idle slice, as a reader stays idle there, unless the feature is given a `transferId`, the reader's own opt-in: it reads there and hands each succeeded read's data to the browser through `TransferState`, under the transfer id and the request key, where the first read of that request takes it, writes it to the slice and sends nothing. When the store's injector is destroyed, every waiting read is aborted and resolves to its failure, and neither a read nor a write changes the slice after that. Writes run side by side, each its own attempt with one idempotency key, or the `idempotencyKey` its call options give, so the app retries by sending again with the same key and the server runs the write once; a write is not aborted on destroy, as `mutate` is not. No store, and no state beyond the slices, is generated (A36). An operation whose slice or method takes a name another operation's feature adds is refused (`names.collision`), since the app composes the features into one store. The module imports the NgRx Signals and runtime names it uses under aliases, and declares its helpers under names that do not start with `with` and a capital, so an operation named `state`, `methods` or `idempotencyKey` generates a feature that compiles. A clash with the app's own store members, or between the features of two apis in one store, cannot be seen at generation; NgRx Signals only warns of it in dev mode, and the page says so. The `angular-fetch` consumer (on `hono` and `angular`, `angular` on `vite`) compiles its components in the page with Angular's JIT compiler, applying `@Component` as a call and marking each `input()` field as the Angular CLI's JIT transform does, and runs tests 1 and 3 to 8 as plain fetch does, with an app interceptor recording the requests, a changed signal input reading again, and the server platform reading nothing. The `angular-ngrx` consumer (on `hono` and `angular`) dispatches the actions through the app's own `provideStore` and reducer: a read's success with its data, a declared error's failure with the typed error, an unexpected error's failure with the effect still answering, one idempotency key per write action, a key the action gives sent again on a second dispatch, two different reads of one operation both answered, and a read of the same request aborted by the next with its failure. The `angular-ngrx-signals` consumer (on `hono` and `angular`) composes `withListTasks` and `withCreateTask` into the app's own `signalStore` beside its own state: a read's data in its slice, a declared error typed in the slice and shown by a component, two different reads of one operation both settled and the same read twice keeping the latest, a write sent again with the key it gave replayed by the server, no read on the server platform unless the feature is given a `transferId`, whose data the browser's first read then takes without sending, and a destroyed store whose waiting read is aborted while its slices stay unchanged.
