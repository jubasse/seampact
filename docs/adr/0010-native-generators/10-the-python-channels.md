### The Python channels

pip installs platform wheels and picks the one that matches the machine, so the binary travels as a wheel. `seampact-ir` runs it on the contract of the PHP channels, and a Python build machine still needs no Node.js ([A48](../../decisions.md#a48)).

- **Contract only.** `seampact-ir` depends on the binary through the contract of "The PHP channels", never on how it is built: the five release assets and `SHA256SUMS`, the command `compile --config <app config> --out <directory>`, its exit codes and its environment.
- **Wheels.** `seampact-compiler` ships one platform wheel per release asset, holding that asset unchanged: manylinux x86_64 and aarch64, macOS x86_64 and arm64, and win_amd64. The tags carry the oldest platform the embedded Node.js runs on: `manylinux_2_28`, and `macosx_13_0`, since pip reads a macOS tag by its major and Node needs macOS 13.5. It has no sdist, so pip never builds the binary. `seampact-ir[compiler]` pulls it, and the extra is optional: as on PHP, the binary is resolved only when an input needs it (a `path` source, or the OpenAPI documents of an app config), so a bundle-only app with `openapi: none` never installs it.
- **Pin.** `seampact-ir` embeds `binaries.json`: the binary version and one SHA-256 per asset, written at release time from `SHA256SUMS`. The root project's `pyproject.toml` overrides it under `[tool.seampact.binary]` with one of: a version with all its hashes, a mirror `url` with all its hashes, or a local `path` with its hash, with the PHP rules for a mirror `url` and a relative `path`. The file the wheel installed is hashed against the pin before any use, like a download.
- **Pin refusals.** They are PHP's: an override with no hash (`binary.pin-missing`); a malformed hash or an unknown asset (`binary.pin-invalid`); a file whose hash differs from the pin (`binary.hash-mismatch`, naming both values); a `[tool.seampact.binary]` table outside the root project's `pyproject.toml` (`binary.override-not-root`, naming the file).
- **Cache.** The cache root is `$XDG_CACHE_HOME/seampact`, else `$HOME/.cache/seampact`; on Windows it is `%LOCALAPPDATA%\seampact`. The binary, from the wheel or a `path` override, is copied owner-only into `<cache root>/<sha256>/` and only that copy runs. The cache, install and check rules are PHP's, with their codes (`binary.cache-unavailable`, `binary.cache-unsafe`); the primary group is read with `os.getgid()` on POSIX; on Windows the per-user ACL of `%LOCALAPPDATA%` stands in for the owner and group checks, as for PHP.
- **Runner.** The runner starts the binary's `compile` with `subprocess.run` on an argument list and `shell=False`, so no shell reads it, in an output directory it creates owner-only, with the contract's environment only and a deadline. The exits are PHP's: `binary.compile-refused`, `binary.compile-timeout` and `binary.compile-failed`.
- **Platforms.** `sys.platform` gives the OS and `platform.machine()` the arch. On Linux the C library is glibc when `os.confstr("CS_GNU_LIBC_VERSION")` answers; otherwise the loader under `/lib` decides, `ld-musl-*` being musl.

  | `sys.platform` | `platform.machine()` | Release asset |
  |---|---|---|
  | `linux`, glibc | `x86_64` | `seampact-linux-x64` |
  | `linux`, glibc | `aarch64` | `seampact-linux-arm64` |
  | `darwin` | `x86_64` | `seampact-darwin-x64` |
  | `darwin` | `arm64` | `seampact-darwin-arm64` |
  | `win32` | `AMD64` | `seampact-win32-x64.exe` |

  The platform unit tests of `seampact-ir` pin these values. Any other row, musl (Alpine) and BSD included, is refused (`binary.platform-unsupported`, naming the detected OS, arch and C library) with the three fixes of the JVM and PHP: use a bundle source; build on a glibc image; or point `path` at your own build, with its hash. The Python guide names the bundle source and the glibc `python:3.x-slim` images.
- **Documents.** Unless `openapi` is `none`, `seampact generate` and `check` run the binary's `generate` or `check` on the app config as the PHP runner does, with its environment, deadline and exits; a refusal is `binary.documents-refused` with its diagnostics.
- **`use` form.** An app config names a pip target as `pypi:<distribution>` (`use: 'pypi:seampact-fastapi'`), beside the npm, Maven and Composer forms of ADR 0011. The Node, JVM and PHP runners leave such an entry to the Python runner, and the Maven form refuses the group `pypi`, so the forms cannot be confused. The app config schema gains the form in a spec change.
- **Until publication.** The compiler and the pip packages are published once, at v1: until then the embedded pin stays empty and there is no `seampact-compiler` wheel on an index. The `version` and `url` overrides download as PHP's do; a `path` override with its hash, or a `url` override on a mirror of your own builds, is the way to the binary in CI and in the test consumers, and an input that needs the binary without one is refused by name (`binary.unpublished`, naming the `path` override). Once the pin is filled, a host with no `seampact-compiler` wheel for its platform is refused with the same code, naming `seampact-ir[compiler]` and the `url` override.
